# logwatch

CLI-утилита для анализа access-логов API генерации видео. Читает логи из stdin построчно, считает метрики (error rate, p50/p95 задержки по эндпоинтам, топ эндпоинтов и пользователей), сравнивает их с порогами SLO и сообщает результат кодом выхода. Её можно запускать вручную, из cron или в CI.

Только стандартная библиотека Python и `python-dotenv`.

## Быстрый старт

```bash
git clone https://github.com/OralbekovAbzal/logwatch.git
cd logwatch

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env              # пороги SLO, можно оставить пустыми

python generate_logs.py 100000 > access.log
python main.py < access.log

# или сразу через пайп, без промежуточного файла
python generate_logs.py 100000 | python main.py
```

## Параметры запуска

| Флаг | По умолчанию | Что делает |
|---|---|---|
| `--format text\|json` | `text` | формат отчёта: текст для человека или JSON для скриптов и CI |
| `--top N` | `5` | сколько строк показывать в топе эндпоинтов и пользователей |
| `--verbose` | выключен | печатает в stderr причину каждой битой строки с её номером |

```bash
python main.py --format json --top 3 < access.log > report.json
python main.py --verbose < access.log 2> parse_errors.txt
```

Пример вывода `--verbose`:

```
Parse error at line 1: expected 7 fields, got 2
```

Неверные аргументы (`--format xml`, отрицательный `--top`) дают сообщение об ошибке и код выхода 2.

## Формат входных строк

```
<ISO-время> <метод> <путь> <статус> <задержка>ms user=<id> model=<модель|->
```

Пример:

```
2026-11-09T12:00:01Z POST /v1/generate 200 1843ms user=u_42 model=kling
2026-11-09T12:00:02Z GET /v1/jobs/j_8f3a 200 166ms user=u_12 model=-
```

- Пути вида `/v1/jobs/<id>` нормализуются в `/v1/jobs/:id`, чтобы все задачи считались одним эндпоинтом.
- Модель обязательна для `/v1/generate`, у остальных эндпоинтов должно стоять `model=-`.
- Битые строки (не тот формат, нет `ms`, статус не число и т.п.) не роняют утилиту. Они пропускаются и считаются в `parse errors`.

## Пример отчёта

Текстовый (по умолчанию):

```
logwatch report
================
Requests:      99941     (parse errors: 59)
Error rate:    1.22%       SLO 2.00%   OK
Status codes
  200   95324
  400   2102
  429   1292
  500   942
  503   281

Top endpoints          requests   p50 ms   p95 ms   SLO 6000
  /v1/generate            48194     2685     4777   OK
  /v1/jobs/:id            39885      103      191   OK
  /v1/models               6890       42       77   OK
  /v1/credits              3996       64      116   OK
  /v1/upload                976     1495     2837   OK

Top users
  u_89      1069
  u_82      1060
  u_7       1054
  u_12      1045
  u_57      1044

Result: OK
```

JSON (`--format json --top 3`):

```json
{
  "total": 99941,
  "parse_errors": 59,
  "error_rate": 0.0122,
  "statuses": {"200": 95324, "400": 2102, "429": 1292, "500": 942, "503": 281},
  "endpoints": [
    {"path": "/v1/generate", "requests": 48194, "p50_ms": 2685, "p95_ms": 4777},
    {"path": "/v1/jobs/:id", "requests": 39885, "p50_ms": 103, "p95_ms": 191},
    {"path": "/v1/models", "requests": 6890, "p50_ms": 42, "p95_ms": 77}
  ],
  "top_users": [
    {"user": "u_89", "requests": 1069},
    {"user": "u_82", "requests": 1060},
    {"user": "u_7", "requests": 1054}
  ],
  "slo": {
    "error_rate": {"limit": 0.02, "ok": true},
    "p95_ms": {"limit": 6000, "ok": true, "violations": []}
  },
  "result": "OK"
}
```

- `error_rate` в JSON — доля от 0 до 1, округлённая до 4 знаков. В текстовом отчёте она показана в процентах.
- `endpoints` и `top_users` отсортированы по убыванию числа запросов и обрезаны до `--top N`.
- Если SLO по p95 нарушен, в `violations` перечисляются пути эндпоинтов, превысивших порог, а `result` равен `SLO VIOLATED`.

## Метрики

| Метрика | Как считается |
|---|---|
| Error rate | доля ответов 5xx от всех корректных строк. 4xx не считаются: это ошибки клиента, а не сервиса |
| p50 / p95 | перцентиль задержки по каждому эндпоинту, метод nearest-rank: `index = ceil(p/100 · n) − 1` по отсортированному списку |
| Top endpoints | эндпоинты по убыванию количества запросов |
| Top users | пользователи по убыванию количества запросов |

## Пороги SLO

Задаются переменными окружения или в `.env`:

| Переменная | По умолчанию | Нарушение, если |
|---|---|---|
| `SLO_ERROR_RATE` | `0.02` (2%) | error rate больше порога |
| `SLO_P95_MS` | `6000` | p95 хотя бы одного эндпоинта больше порога |

Если значение некорректное (не число или вне допустимого диапазона), утилита пишет ошибку в stderr и завершается с кодом 2.

## Коды выхода

| Код | Значение |
|---|---|
| `0` | отчёт построен, все SLO соблюдены |
| `1` | отчёт построен, но хотя бы один порог SLO нарушен |
| `2` | неверные аргументы, ошибка конфигурации или ни одной корректной строки на входе, отчёт не выводится |

Отчёт всегда идёт в stdout, ошибки в stderr. Поэтому вывод можно перенаправлять в файл или передавать дальше по пайпу:

```bash
python main.py < access.log > report.txt
echo $?
```

## Генератор тестовых логов

```bash
python generate_logs.py <количество строк> [--seed N]
```

- Одинаковый `--seed` (по умолчанию 42) даёт одинаковый лог, поэтому результаты воспроизводимы.
- Распределения похожи на реальный трафик: около 95% ответов 200, есть 4xx/5xx, задержка зависит от эндпоинта и статуса.
- Примерно 0,05% строк намеренно битые, чтобы проверить обработку ошибок парсера.

## Структура

```
logwatch/
├── main.py            # точка входа: чтение stdin, вызов модулей, коды выхода
├── models.py          # LogEntry, ParseError, ConfigError
├── parser.py          # разбор одной строки в LogEntry, нормализация пути
├── stats.py           # накопление агрегатов, перцентили, проверка SLO
├── report.py          # текстовый и JSON-отчёт
├── config.py          # чтение и проверка порогов SLO
├── generate_logs.py   # генератор тестовых логов
├── tests/
│   └── parser_test.py # тесты парсера
└── .github/workflows/ # CI: тесты на каждый PR в main
```

`parser.py` и `stats.py` не читают stdin, ничего не печатают и не завершают программу. Всё это делает `main.py`, поэтому модули легко тестировать по отдельности.

## Производительность

Утилита не хранит строки и объекты `LogEntry`, только счётчики и списки задержек по эндпоинтам. Поэтому вход читается потоком и не загружается в память целиком.

Замер на 1 000 000 строк из генератора (MacBook Air M4, Python 3.15):

| Формат | Время |
|---|---|
| `--format text` | ~5,9 с |
| `--format json` | ~5,9 с |

Требование — не дольше 10 секунд на миллион строк. Почти всё время уходит на разбор строк, формат отчёта на скорость не влияет.

```bash
python generate_logs.py 1000000 > big.log
time python main.py < big.log > /dev/null
```

## Тесты

```bash
python -m tests.parser_test
```

Если вывода нет, значит, все проверки прошли. Тесты автоматически запускаются в GitHub Actions на каждый pull request в `main`.

## В работе

- тесты для перцентиля, конфигурации и кодов выхода
- сообщения в stderr через `logging` вместо прямой записи
- период логов в отчёте
